# 配信の動画そのものを落とすとき

**この箱からは落とせない。Actions でやる。**
使うのは `.github/workflows/clip_fetch.yml`（「切り抜きの mp4 を取る」）。

## まず、使い方

1. Actions で **「切り抜きの mp4 を取る」** を `workflow_dispatch` で押す
2. 入れるもの

   | 入力 | 何を入れるか |
   | --- | --- |
   | `video` | 配信ID（`f3W2JxAHsQs` など） |
   | `sections` | 区間。コンマ区切り。`0:54:10-0:55:30,0:57:40-0:59:20` |
   | `height` | 縦の画素数。既定 720。重ければ 480 |
   | `rounds` | 口を全部当たるのを何周するか。既定3 |
   | `pause` | 1周ごとに空ける秒数。既定120 |

3. 終わったら、その run の **Artifacts** から `clip-<配信ID>-<run_id>` を落とす。
   中に区間ぶんの mp4 と `report.md` が入っている

**落とせなかった回も artifact は出る。** 中の `report.md` に「どの口が、
どう断ってきたか」の表が入っている。**通らなかった記録が次の判断の材料になる**ので、
空振りでも捨てない。

`clip-cut`（どこを切るか）で出た「長め」の区間を、そのまま `sections` に入れる。

## この箱から落とせない理由

`yt-dlp` は形式の一覧までは取れる。取りに行った瞬間に 403 Forbidden になる。
ffmpeg 経由でも、`yt-dlp` 自身の downloader でも、HLS でも DASH でも同じ。

媒体の URL（`googlevideo.com`）は**取りに来た IP に紐づけて署名されている**
（`ip=` が `sparams` に入っている＝署名の対象）。
この箱の出口はプロキシで、**接続ごとに別の IP に変わる**。

    $ for i in 1 2 3; do curl -s https://api.ipify.org; echo; done
    160.79.106.131
    160.79.106.132
    160.79.106.129

抽出したときの IP と、取りに行くときの IP が一致しない。だから断られる。
`http_proxy` を ffmpeg に渡しても変わらない。**出口そのものの話**なので。

ランナーは1つの IP で最後まで通るので、そこが塞がらない。

## PO Token は要る。ただしそれだけでは足りない

今の YouTube は媒体の URL に `pot` が無いとほぼ弾く。BotGuard を deno で回して
作る（`bgutil-ytdlp-pot-provider` 2.0.0）。ワークフローの
**「PO Token が本当に作れるか見る」**が、それを確かめる step。

**ここを黙って素通りさせない。** 作れていないのに「ボット確認が出た」と読むと、
口の当たり直しを何時間も続けることになる。実際そうなった。

`n challenge` は deno があれば解ける（`yt-dlp-ejs` ＋ `deno`）。
この箱にも `/opt/deno/bin/deno` が入っている。

**PO Token があっても、IP の評判が悪ければ `Sign in to confirm you're not a bot`
は出る。** ランナーの IP は世界中の取得に使われているので、出るほうが多い。

### 2026-09-13 に実測したこと

**Cookie 無しでは、いま1本も取れない。** 別々のランナー3台で、9つの口を3周ずつ
（27回×3台＝81回）当たって、**81回すべて `Sign in to confirm you're not a bot`。**
PO Token は作れている（step 6 が通っている）。

しかも**断られるのが速い。1.2〜2.0秒。** これが効く。
遅れて断られるなら「評判の計算に乗って、たまたま落ちた」だが、
1秒台で即答するのは**player に聞いた時点で門前払い**という意味になる。
`tv_simply` も `android_vr` も `ios` も同じ秒数で同じ文句を返す。
**口の選び方では抜けられない。粘る回数の問題でもない。**

| 回 | 時刻(UTC) | ランナー | 結果 |
| --- | --- | --- | --- |
| [34783187066](https://github.com/Ayato-kosaka/live-streaming/actions/runs/34783187066) | 21:14 | 別々 | 27回すべてボット確認 |
| [34783286496](https://github.com/Ayato-kosaka/live-streaming/actions/runs/34783286496) | 21:15 | 別々 | 27回すべてボット確認 |
| [34783340160](https://github.com/Ayato-kosaka/live-streaming/actions/runs/34783340160) | 21:17 | 別々 | 27回すべてボット確認 |

**一方、毎晩の取り込み（`schedule_fetch_chat.yml`）は同じランナーで通っている。**
違いは Cookie を使っていることだけ。だから**Cookie が答え**だと言える。
入れてもらう手順は issue #322。

## 落とし方の作り

`tools/clip/fetch.py`。要点は2つ。

**(1) 区間だけ取る。** `--download-sections *開始-終了`。1日目は10時間52分あって、
丸ごと落とすと取れても30分、断られたら30分捨てる。1分半の区間なら20〜40秒で終わる。

**(2) 落としに行く前に、口が通るかだけ聞く。** ボット確認は**媒体を取りに行く前、
player に聞いた時点で**出る。`--print` で形式を聞けば数秒で分かるので、
全部の口を先に当たって通る口を1つ見つけてから、その口だけで落とす。

古い `day1_cut.py` は口を1つずつ当たっては落としに行っていたので、1周に何分も掛かって
「24回試して6時間」になっていた。**当たりの1周を1分にすれば、粘る意味が出る。**

**絵コンテ（storyboard）だけ返る状態を「通った」と数えない。** ボット確認のとき
yt-dlp は終了コード 0 のまま `sb0 / mhtml` だけ並べることがある。
`fetch.py` は `avc1 / vp9 / av01` が見えたときだけ通ったと数える。

## Cookie（`YOUTUBE_COOKIES` を使い回す）

**`YOUTUBE_COOKIES` を使ってよい。** あやとの言葉（2026-09-22。issue #322）:

> YOUTUBE_COOKIES を使いまわしてください。これ、本アカじゃない、yt dlp 専用クッキー。

ここには長いあいだ「**絶対に触らない。本アカだから、巻き込むと毎晩の取り込みごと
止まる**」と書いてあったが、**前提が違っていた。** あれは本人のアカウントではなく
yt-dlp 専用に取ったもので、壊れても本人の YouTube には関係がない。
別口（`YOUTUBE_COOKIES_CLIP`）を頼む理由も、そこで消えた（#322 は閉じてよい）。

**ただし、技術的な危なさは残る。アカウントの話とは別なので、そこは守る。**

1. **毎晩の取り込みと同じ時間に走らせない。** `schedule_fetch_chat.yml` は
   最後の step で `cookies/update@v3` を使い、**その回のセッションを Secret に
   書き戻す。** 同時に走ると、古いほうが新しいほうを上書きして**両方が締め出される。**
   cron は 20:00 UTC だが、**1時間49分〜3時間32分遅れて**発火する（実測）。
   **21:30〜23:59 UTC は避ける。**
2. **書き戻さない。** 使う側は `cookies@v3`（読むだけ）で止めて、
   `cookies/update@v3` を**呼ばない。** 持ち回りの責任は毎晩の取り込み1本に置く。
   ここが2本になると、どちらが最新かを誰も知らなくなる
3. **リポジトリ全体で `cookies/update@v3` を呼ぶのは `schedule_fetch_chat.yml` だけ**、
   という状態を保つ。増えていないかは grep で見る

## 渡し口は artifact しかない

置き場（Firebase Storage）に書けるのは Functions だけで（#283）、あの口は
小さな絵しか受け取らない。この箱には `FIREBASE_SERVICE_ACCOUNT` も無い。

artifact は30日で消える。**要るものはその場で落とす。**

## コメントの記録は、この箱でも取れる

`--write-subs --sub-langs live_chat` は別の口なので通る。
各行に `videoOffsetTimeMsec` が入っていて、**配信内の位置がそのまま取れる。**
15時間を目で探さずに済む。**Cookie は使わない。**
