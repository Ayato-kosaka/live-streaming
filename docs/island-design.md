# あやと島 — デザイン仕様

**この文書は拘束力を持つ。** 迷ったらここに戻る。ここに書いてあることに反する実装はしない。
新しく作るものは、作る前にここを読む。守れない理由ができたときは、実装を曲げるのではなく
この文書を直してから実装する。

目指す水準は「任天堂が作ったぐらい」。**情報が正しく並んでいるだけでは不合格**とする。

---

## 1. 絵文字は使わない

**UI にも、コンテンツにも、絵文字を1文字も置かない。** 例外はない。

なぜ:
- 端末とOSで形が変わる。Android と iPhone で別のサイトに見える
- どうぶつの森の絵の中に、まったく違う絵柄のものが混ざる。いちばん安く見える原因
- 大きさと位置が揃わない。ベースラインが合わず、並べると汚くなる

置き換え先:

| 何を | 何に |
| --- | --- |
| 場所・物（建物、料理、たき火） | **スプライト**（`site/public/sprites/*.webp`。無ければ `tools/sprites/` で焼く） |
| 記号・操作（ダウンロード、外部リンク、閉じる、開く） | **`components/ui/Icon.tsx` の自前 SVG** |
| ブランド（App Store、Google Play、Instagram、YouTube） | **公式マークを写した自前 SVG**（`Icon.tsx`） |
| 国旗 | **`components/ui/Flag.tsx`**（帯・十字・カントンの組み合わせで描く） |

新しい印が要るときは、絵文字で済ませずに **SVG を1つ増やす**。それがこのサイトの作り方。

`content/*.ts` の `emoji` フィールドは残っているが **画面に出してはいけない**。
（配信のOBS側など、サイト外で使っているものがあるため消していない）

### ひとつだけ例外

**配信のタイトルと、視聴者さんが書いた文章は、そのまま出す。**
「アゼルバイジャン🇦🇿に到着しました」は YouTube に実在するタイトルで、
これは引用なので勝手に直さない。自分たちが書く文字にだけ、この決まりを適用する。

丸数字（①）や矢印（→ ⇄ ◎）のような記号は絵文字ではない。
端末で形が変わらないので、文章の中で使うぶんには構わない。
ただし **ボタンや見出しの印としては使わない**。それは Icon にする。

## 2. 絵の原則（どうぶつの森に寄せる）

1. **輪郭線を引かない。** 形は色の差だけで見せる
2. **環境光をとても強くする。** 影で立体を作らず、明るさの差で作る
3. **接地影を焼き込む。** 物が地面から浮かないように
4. **彩度と明度をどちらも高く。** 彩度だけ上げると毒々しくなる
5. **急な変化を作らない。** グラデーションと丸い角。四角い切り替わりを作らない

**この5つは、焼いたスプライトだけの話ではない。SVG のアイコンにも同じだけ効かせる。**
平らな単色のアイコンを、階調のあるスプライトの隣に置くと、別の世界のものに見える。
SVG にも上からの光（上を 8% ほど明るくする縦のグラデーション）を入れる。
1つずつ直すのではなく、共通の `<defs>` に1つ置いて全部から参照する。

スプライトの焼き方は [`island-concept.md`](./island-concept.md) を見る。

## 3. 触りごこちの原則

1. **押す場所は物そのもの。** ヒットエリアが絵からずれていると、人は「壊れている」と感じる
2. **指で押せる最小 48px。** どんなに小さい絵でも確保する
3. **「押せる」は厚みで伝える。合図は厚み1種類だけ。**
   押せるものには下に厚みがある。押せないものは完全に平ら。
   光らせない。きらめかせない。色を変えない。**厚みだけ。**
   遠目に分かる大きさで付ける（48px のボタンで 6px、30px の札で 4px）。
   混ぜると、どれが合図でどれが飾りか分からなくなる（夜のランタンと発光を混同した前例あり）。

   **地面に落ちる影と、遠目で取り違えられないようにする。**
   厚みは真下へ、ぼかさない。落ち影は右下へずれて、3px ぼける。
   **向きとぼかしの両方を違える。片方だけでは足りない。**
   `--shadow-1` が `1px 3px 0`、`--pop-sm` が `0 4px 0` だったとき、
   横1px・縦1pxしか違わず、押せないのに厚みのあるものが21面で 53 個あった
   （`docs/island-world.md` 7.8）。合図が見分けられないのは、合図が2つあるのと同じ。

   **例外は1つだけ。一面に並ぶマスが全部押せるときは、1枚ずつに厚みを付けない。**
   並びそのものが合図になる（本物の図鑑の一覧がそうで、マスは平ら。
   `docs/ac-reference.md` 7章2）。厚みの決まりがあるのは
   「どれが押せるのか」を迷わせないためなので、**迷いようが無いときは要らない。**
   料理32マス・企画8マス・住人22マスがこれ。

   **ただし、その並びの中に押せないマスを1枚でも混ぜてはいけない。**
   混ぜた瞬間、この例外が嘘になる。混ぜたくなったら、並びの外に出す。
4. **注目させるのは一度に1つ。** 名前が出るのはいちばん近い1つだけ
5. **反応を返す。** 近づいたら弾む、押したら沈む
6. **勝手に消さない。** 吹き出しは押すまで出ないし、閉じるまで消えない
7. **主役の優先度を守る。** 重なったときは 入口（建物）＞ 住人。
   住人との会話はおまけなので、行き先を塞いではいけない

### 動きは React の外で

**毎フレーム `setState` を呼ばない。** カメラ・住人・あやとの位置は `ref` から DOM に直接書く。
React の再描画は「状態が変わったとき」だけ（吹き出しが開いた、入口が選ばれた、など）。

島には 160 枚以上のスプライトがある。毎フレーム全部を作り直すと、
スマホで目に見えてカクつく。**滑らかさは実装の都合より優先する。**

## 4. 情報の見せ方

### 長い文章は折りたたむ

**1画面に収まらない説明文を、そのまま縦に並べない。**
見出しだけが並んでいて、押すと開く形にする（`<details>` ベースの `Fold`）。

- 旅のしおりのような「読む人が目次から探すもの」は必ず折りたたみ
- 国ごとの見どころのような「たくさんあるもの」も、要点だけ見せて本文は畳む
- 開いた状態を初期値にしていいのは、そのページで最も伝えたい1つだけ

「ポンポンポンと押して進める」感触を作る。スクロールで探させない。

### 数字は意味のあるものだけ

飾りの数字を置かない。「0回、戻らない」のような、読んで何も分からない数字は消す。
出すなら、その数字を見て**何かが分かる**ものにする（1,541km / 6カ国 / 出発まで あと◯日）。

### 読み込み中と、空っぽの形を必ず作る

外から取ってくるもの（掲示板の投稿・投げ銭の額・今日の数字）は、
**出るまでのあいだ何も無い時間がある。** そこを作らないと、面ごとにばらばらになる。

- **読み込み中** — 場所だけ先に取る。中身の形をした薄い板を置く。
  ぐるぐる回すものは使わない（島に回るものは無い）
- **空っぽ** — 「まだ何も無い」で終わらせない。**次にすることを1つ書く。**
  「まだ何も貼られていない。いちばん乗りだよ。」のように
- **取れなかった** — 焼き込んである値に静かに落ちる。エラーを出さない。
  見ている人には関係のない話なので

### 地図は絵で描く

一覧や表で済ませない。旅・場所・ルートは **SVG の地図**にする。
地形は実際の形に沿わせ、塗りと線は島と同じテイスト（輪郭線なし・柔らかい色・丸い角）にする。

## 5. 言葉の原則

1. **説明口調を使わない。**「〜できます」「〜になっています」と書かない
2. **ボタンは動作そのものの言葉にする。**「送信」ではなく「はりだす」、「詳細」ではなく「はいる」
3. **見出しは、読む人の頭の中の問いにする。**「これまでのあしあと」ではなく
   「これまで、どこへ行って何を作ったんだろう」
4. **案内役のカモメは、見出しの言い直しをしない。**「ここでどう遊ぶか」だけを言う

### 住人のセリフ

島にいるのは視聴者さん本人。**口調はその人のものを写す。**
ただし **内容は「初めて来た人に意味のあること」でなければならない。**

配信のコメントをそのまま持ってくるのは禁止。
文脈のないコメント（「油はコロッケの半分の高さね」「ハエも仕事してる」）は、
初めて来た人には意味が通らない。口調だけ借りて、中身は島の案内かあやとの事実にする。

良い例:
> あやとさ〜ん、初めてならね、「いまどこ」を見てみて。いまいる場所が書いてあるよぉ〜

悪い例:
> 油はコロッケの半分の高さね。少ないなら焼きコロッケ風にすれば安心だよー

## 6. 情報設計（島の入口）

**島に建っているものは、全部押せる。押せないものは建物にしない。**

建物の形をしていて押せないものを置くと、人はそれを押して、何も起きなくて、
「壊れている」と思う。景色が要るなら、木・岩・花・柵を置く。建物は置かない。

ただし、**看板を出して案内するのは6つだけ**にする。
下のバー（スマホ）と、島の外のページの頭に並ぶのはこの6つ。残りは静かに置いておく。
見つけた人が押せる、という状態にする。

**島の上には、名前を並べない。** 看板の6つも、島の上では他の4軒と同じように黙って建っている。
名前が出るのは**近づいた1軒だけ**（3-4）。6枚を常に出していたときは、
スマホ 390×844 の1画面に札6枚・名前40文字が並び、UI が島の絵を 23% 覆っていた。
本物のあつ森は、島を歩いているあいだ画面に字が1文字も無い
（`/tmp/acref/ref_NH_Plaza_Exercise.jpg`）。**看板を出すかどうかと、
それを島の上に貼っておくかどうかは、別の話。**

島の上に常に出ていてよいのは、次の2つだけ。どちらも**1日に1つまで**で、
どちらも「今日ここが違う」を言っている。

| 何 | いつ | 何文字 |
| --- | --- | --- |
| 「！」の丸 | 今日の板が指している建物に1つ | 1 |
| 「あと◯日」のシール | 出発が近い入口（`countdown`）に1つ | 4〜5 |

### 入口の名前は、中身をそのまま言う

**島の固有名詞を名前にしない。** 「たき火広場」「旅の桟橋」「いまのポスト」は、
名前を見ただけでは中に何があるか分からない。探している人は、名前を1つずつ
開いて確かめることになる。それは動線が無いのと同じ。

**RPG らしさは建物の絵が持つ。札は答えだけを言う。**
島に立っているのは家であり、やぐらであり、道しるべだが、その上に出る名前は
「あやとのこと」「配信」「歩いた国」にする。絵と名前は別々の仕事をする。

名前を決めたら、**絵がその名前を指しているかを見る。** 指していなければ絵を作り直す。
たき火は「あやと本人」を指さない。桟橋は「歩いた国」を指さない。
郵便受けは「いま居る場所」を指さない。この3つは絵のほうを替えた。

添え書き（`blurb`）も同じ。**押す前に答えが読めるようにする。**
「そこで何が分かるか」の説明ではなく、分かることそのものを1行で書く。

### 看板を出す6つ

| 入口 | 行き先 | 建っているもの | 中にあるもの |
| --- | --- | --- | --- |
| あやとのこと | `/about` | あやとの家 | はじめまして・ここまでの道のり・島でやってること |
| 配信 | `/streams` | やぐら | 配信の型5つ |
| アプリ | `/apps` | 工房 | なに食べよ・なにこれオーディオガイド |
| これから | `/next` | テント | 直近の企画。**いちばん目立たせる**（通知バッジを付ける） |
| 企画をだす | `/board` | 掲示板 | みんなの提案 |
| 歩いた国 | `/map` | 国旗を掛けた道しるべ | これまでに歩いた国 |

### 看板は出さないが、押せば入れるもの

| 入口 | 行き先 | 建っているもの |
| --- | --- | --- |
| 作った料理 | `/kitchen` | 台所の小屋 |
| 伝説の企画 | `/legends` | 丘の館 |
| いまどこ | `/now` | ピンを立てた地球儀 |
| 住んでる人 | `/friends` | 小さいテント |

**この4つは島の直下にある。** 以前は「配信の下」「あやとのことの下」に
ぶら下げていたが、押せる建物が島に建っている以上、親子にすると
パンくずと実際の行き方が食い違う。

パンくずは、この関係と必ず一致させる。

**名前はここが決まり、実装の出どころは `site/components/island/layout.ts`。**
h1・パンくず・OG・住人のセリフ・ヘッダーの札は、全部この名前にそろえる。

## 7. 出す前に必ず回すもの

```bash
cd site && NEXT_DIST_DIR=.next-verify npx next build
node ../tools/sprites/noemoji.mjs       # 書き出したHTMLに絵文字が残っていないか
python3 -m http.server 4321 --directory .next-verify &
cd ../tools/sprites && node crawl.mjs     # 全ページの h1・JSエラー・横あふれ・リンク切れ
node align.mjs                            # 建物の絵と当たり判定・合図のズレ
cd .. && python3 tools/sprites/audit.py   # スプライト1枚ずつ、上の5原則を数で
SPORT=4321 STATE=1 node tools/sprites/clutter.mjs   # 1画面に何個・何文字・UI が何%
```

`clutter.mjs` は「ごちゃごちゃしている」を主観で言わないための道具。
390×844 の1画面に載っているものの数と、出ている字の数と、UI が島の絵を
覆っている割合を出す。**`STATE=1` を付けて測る。** 付けないと住人の名札が
出ていない日を測ることになり、本番より静かな数字が出る。

`audit.py` は 2章の原則をそのまま測る（輪郭線・接地影・暗さ・彩度）。
**「浮いている絵」を目で探さない。** 300枚を並べて見ても、どれが原則を
外しているかは分からない。数にしてから並べ替える。
そう焼いてあるのが正しいものは、道具の中に理由を添えて別に出してある。
消してはいけない——黙って外すと、そこが本当に壊れたときに気づけない。

**「見た目がズレている」は必ず数字で確かめる。** 目視だけで通さない。
スクリーンショットは、スマホの引き・スマホの寄り・PC の3つを最低限見る。
