# 0001 文書を5つの種別に分け、決まったことは仕様と決定の記録に書く

- 日付: 2026-11-22
- 状態: 採用
- 決めた人: あやと（仕様）／運営（設計）
- 仕様の条: `docs/README.md` D-1〜D-8

## 状況
あやと（2026-11-22）:「ドキュメントが結構散らかってる。検討資料・メモ資料みたいなのが散らばってる。業界標準になってない。もっと決まったことをガチッと書くべき。厳密に決まったことを書く、というお堅い仕事ができてない」

数えた（master `dce926b`）。
- `docs/` に46本・42,311行が平らに並ぶ。仕様・手順・現状の表・日付つきの記録・決める前の資料が、同じ箱・同じ名前の付けかた（`island-*.md`）で混ざっている
- いちばん大きい `island-misses.md` は 19,101行（全体の45%）で、`CLAUDE.md` は「作る前に必ず読む」と言っている
- 設計の決定は issue の本文とコメントに置かれていて（#1201・#1274）、決まったあとの正がどこかを言う場所が無い
- リポジトリの直下に、島より前の作業の md が8本残っている
- `CLAUDE.md` は612行。立ち位置・手順・つまずき・経緯が1枚に入っている

## 決定
- 文書の種別を5つとする: 仕様・決定・手順・台帳・記録
- 決まったことは仕様（`docs/spec/`）に書く。なぜ決めたかは決定の記録（`docs/adr/`）に1決定1枚で書く
- issue は作業の単位とする。設計を issue に置いたままにしない
- 全部の文書を `docs/README.md` の台帳に1行ずつ載せ、種別を付ける。載っていない文書は置けない（見張りで止める）
- 既存の文書の置き場は動かさない。新しく書くものから、種別ごとの置き場に置く

## 理由
- 仕様と記録が混ざっていると、「作る前に読むもの」が1万9千行になり、読まれない。読まれない決まりは守られない
- 決定が issue に在ると、閉じたあと・コメントが増えたあとに、何が正か分からなくなる。v1 の決定を v2 で取り消したことも、コメントを最後まで読まないと分からない
- 仕様（いま決まっていること）と決定の記録（経緯）を分けるのは、仕様を短く保つため。経緯を仕様に書くと、仕様が毎回伸びる
- 既存の置き場を動かさないのは、`docs/` の文書が 2,800か所以上から名指しされているため（コード・見張り・ワークフロー・スキル）。動かすと、その全部を同じ日に直すことになり、ほかの作業の枝と衝突する

## 捨てた案
- **既存の46本を種別ごとの箱へ移す。** 見た目はいちばん片づくが、名指しを 2,800か所直す必要がある。台帳で種別を付ければ、読む側は同じものを得る
- **1本の大きな設計書にまとめる。** 1万行を超えた文書が既に読まれていない
- **文書の頭に種別の印（front matter）だけを付ける。** 一覧できない。台帳と見張りのほうが、足し忘れを止められる

## 影響
- 新設: `docs/README.md`（台帳と決まり）・`docs/spec/`・`docs/adr/`・`python/docs_index_selftest.py`
- `CLAUDE.md` を、いつも守ることと、どこを読むか、だけにする（別 issue）
- `island-misses.md` から決めごとを仕様へ写し、「作る前に読むもの」を短くする（別 issue）
- 直下の古い md と、古くなった手引きを片づける（別 issue）
