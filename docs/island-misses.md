# 言われたことと、外した理由

**あやとに指摘されたことを、ここに残す。** 直したかどうかではなく、
**なぜ外したか**と、**次に同じ形で外さないための決めごと**を書く。

あやとの言葉（2026-09-09）:

> 君なんかいも指摘してるけど、私と認識あわないまま進めすぎよ。
> それで、毎回もぐら叩きになってることに気付け。
> まずは、自分が指摘されたら、原因と対策を自分で記憶する仕組みが必要。

もぐら叩きになるのは、**1件ずつ直して、外し方を残していない**から。
セッションが変わると、同じ外し方をもう一度する。ここはそのための場所。

**直したら消す、ではない。** 直したあとも残す。理由は「同じ形で外しかけた
とき、ここを読めば止まれる」ため。

## 決めごと（先に読む）

### 1. 作る前に、何を作るかを1行で言って合わせる

指示に幅があるとき、**自分に都合のいい読み方で埋めない。** 作る対象・範囲・
出来上がりの形を1行で言って、違ったら言ってもらう。1行を惜しんで作り直す
ほうがずっと高くつく。

「地図を貼って」で国の地図を切り取って出したのがこれ（下の #3）。

### 2. 直したと言う前に、**本番の値**で確かめる

差し込み（`tools/sprites/asme.mjs`）に本番と違う値を置くと、直っていない
ものが直って見える。**差し込みの値は本番から取ってくる。**
合否は、見た目ではなく**通信やデータ**で決める。

### 3. 名簿を手で作らない。**もうある導出を使う**

街・国・企画の一覧は、旅程から導出されている（`VISIT_CITIES`,
`MAYBE_CITIES`, `visitCitiesOf`）。手で書くと、旅程が変わったときに
**片方だけ古くなる。**

### 4. 可否を預けない。**決めて、やって、報告する**

あやとの言葉（2026-09-09）:

> デプロイの可否は自分で判断してね。（略）あなたがあやと島運営者です。
> つまり、システムの判断は全てあなたの責務。
> 私はいち、オーナーユーザーとして、意見を言ってるだけ。

「出していいですか」「どちらにしますか」と聞くのは、**判断を投げていること。**
意見はもらう。それをどう反映するかを決めるのは、こちらの仕事。

**品質の可否もこちらが決める。** 出す前に自分で見て、届いていなければ出さない。
出してから言われて下ろすのは、判断をしていないのと同じ（#6）。

### 5. **言われたところだけ直さない。横に展開する**

あやとの言葉（2026-09-10）:

> Firestore 見直したはず。データ直したら、同じ反省点としてルーティングも
> 直すのが常識の仕事の進め方ですよ。（略）
> 言われたことだけ直してる感が半端ないんですよあなた。

1件直したら、**同じ理由で壊れているところを探しに行く。**
データを直したら、それを読む画面・ルーティング・文言・導線まで見る。
指摘は「見つかった1件」であって、「直すべき全部」ではない。

### 6. **面の構成は、こちらが設計する**

> そもそもこの画面入らなくて cards に統合すべきでは？
> ちゃんと、システム管理者として広い目で設計してる？
> 私に現場監督をさせるな。

「この画面要る？」「統合すべきでは？」を**あやとに言わせた時点で負け。**
似た面が2つあれば、どちらが良いかを決めて寄せる。重複した説明があれば消す。
使いにくい導線は、言われる前に直す。

**あやとは意見を言う人であって、現場監督ではない。**

### 7. **画面で、システムの仕様を説明しない**

> システムの仕様の説明をするのはやめて欲しい。
> 例えば、「名前が出ているのは、島に名前を出してよいと言ってくれた人です。
> 出していない人も、絵はそのまま立っています。」
> この文章そもそもすごくわかりにくいし、仕様の説明はしないで欲しい。

書いてよいのは、**その人がこれから何をするか／何が起きるか**だけ。
「どういう条件でこう出しているか」は中の話で、読む人には要らない。
迷ったら消す。**説明が要る画面は、画面のほうが間違っている。**

### 8. 「あとで」を自分で決めない

あやとは「旅が終わってからの作業に後回しをするつもりはない」と言っている。
重い・危ないと思ったら、**後回しにするのではなく、そう言って判断を仰ぐ。**

### #8 面を1枚に積み上げて、8,336px にした（2026-09-10）

**言われたこと**「オーナーマイページ画面が整理されてなさすぎる。ux 悪すぎ。
縦長すぎる。全くいけてない。どう森レベルに持っていけるように、水平展開して

**原因** じぶんのこと（`/me`）に、用事の違うものを**足すたびに1枚ずつ紙を

390px 幅で 8,336px、スマホ10画面ぶんあった。

「どこに置くか」ではなく「下に足す」を選んだこと。** 面の構成を設計し直す
機会が一度も無いまま10枚になった。

しかも積んである紙のうち**3枚（付箋・企画・カード）が「溜まると伸びる」もの**
だった。畳み（`Longer`）は入れてあったが、畳んだものが3つ縦に並べば、
やはり下は遠くなる。**畳むだけでは足りない。**

**対策** 基準の7章（新設）。

- 用事の違うものは**面ごと分ける**。運営の道具は `/me/desk` に出した
- 増えるものが2つ以上ある面は、**札で切り替えて同時に1つしか出さない**
- 作る前に「これが200件になったら」を1度考える。**0件・3件・40件・200件で
  撮って確かめる**（`NOTES=` を `tools/sprites/asme.mjs` に渡す）

**同じ形を他でも探した。** あやと島カード（`/cards`）が、日ごとの棚を
1日ずつ無限に積んでいた（旅に出れば毎日1つ増える）。畳んで 3,430 → 1,982px。

### #12 「言われたところ」しか直さず、その裏の道を直さなかった（2026-09-10）

**言われたこと**「Firestore 見直したはず。データ直したら、同じ反省点として
ルーティングも直すのが常識の仕事の進め方ですよ。」

**原因** 写真のデータを直したとき、**それを読む面・その面への入口・その面の
URL** まで見にいっていない。実際に壊れていたのはこの3つ。

1. `/nordic/photos/`（うしろにスラッシュ1本）が**島の玄関を 200 で返していた。**
   Firebase の受け皿（`"source": "**"` → `/index.html`）に落ちるため。
   404 にすらならないので、踏んだ人には何が起きたのか分からない。
   **`/nordic/photos` だけの話ではなく、島じゅうの URL がそうだった**
   （`/nordic/day/1/` も同じ）。`"trailingSlash": false` を足して直した
2. `/nordic` からの入口は、写真が貼られるまで出ない1行だけ。
   旅程表の 7画面ぶんの下にあって、**入れないに等しかった**
3. カードの企画の札（`/next#food-wine-fest`）を押しても、その段まで**送られない。**
   目当ての段が 3,055px にあるのに、止まったのは 238px。面が出てから伸びるので、
   ブラウザが `#` を探す時点ではまだその高さに無い。**島の面はどこも中身を
   取りにいくので、この面だけの話ではない**（`components/ui/HashJump.tsx`）

**対策** 決めごと5。データを直したら、それを読む画面・その面への入口・
URL・文言まで、**同じ理由で壊れているところを探しに行く。**
そして **curl の 200 を「入れる」と読まない。** curl は
`/nordic/photos` しか叩いていないし、スラッシュ1本違いも、押したあと
どこへ着くかも見ていない。**ログインして、実際に押して確かめる。**

### #13 「代表の1人」を勝手に立てた（2026-09-10）

**言われたこと**「代表でキャラクターを埋めるのはやめて欲しい。」
「たいpi のキャラクターが見切れてる。あと大きさも不揃い。」

**原因** 1枚の写真に4人ぶんカードがあるのに、開いた先が**1人目を入れた絵**で
始まっていた。その人がその写真の代表のように見える。
`/about` の帯も同じことをしていた。

見切れと不揃いは、台帳の `x/y/scale` を**そのまま**使っていたため。
既定値は ID から散らしてあり、`x = 0.864 / scale = 1.046` は右端を 4% はみ出す。
散らしたのは「一覧に同じ写真のカードが人数ぶん並ぶ」ころの都合で、
**一覧が写真1枚につき1マスになった時点で、理由が消えていた。**
消えた理由の名残を、消さずに残していた。

**対策** 決めごと4と6。**まとめ方を変えたら、その前提で入れた工夫を
見直す。** 出す前に、本番と同じ値で撮って自分の目で見る
（本番の4人ぶんで撮っていれば、はみ出しはその場で見えた）。

### #14 「島の大きさ＝日数」を、主役の1枚にもそのまま当てた（2026-09-10）

**言われたこと**「z-sp-nordic.png は、大きな水色の皿の上に小さな茶色い塊が
乗っているだけで、島に見えません」「北欧は明日あやとが出発する、いま一番
見せたい島です。ここが一番弱いまま出すことはできません」。

**原因** `docs/island-atlas.md` 3章の下駄（`r = √(BASE² + K²・日数)`）は、
**島を124pxの行に小さく並べていたころに、「島に見えなくなる」のを避けるために
決めた値**だった。それを、全画面で1つを主役に出す新しい画面へそのまま持ってきた。
17日の島は 438日の島の 3.5分の1なので、皿に対して豆粒になった。

**式そのものは正しい。当てる先を間違えた。**
しかも「小さい島が寂しい」とは自分で報告に書いていて、**弱いと分かったまま
出そうとした**（水準の1に反する）。

**対策** 数式や定数を別の画面へ持っていくときは、**それが何のために決められた
値かを見る。** 一覧のために決めた値は、主役のために決めた値ではない。
そして、自分で「弱い」と思ったものは出さない。

直しかた: 主役は枠いっぱいに寄せ、**大きさの比べ合いは航路の丸が引き受ける**
（丸の直径＝島の半径。面積が日数に比例する）。式は1文字も変えていない。

### #15 読めなかったことを、0円と同じ絵にした（2026-09-10）

**言われたこと**「足代が読めなかったとき、絵が嘘をつく。（略）落ちるたびに
『まだ1円も集まっていない島』が視聴者さんに見えるのは、支援してくれた人に
対して失礼です」「引き継いだものでも、嘘なら直すのがこちらの責務です」。

**原因** `useFund()` は読めないときも 0以下のときも `null` を返す。
それを `pct = fund ? … : 0` と書いて、**0% の更地**として描いていた。
額のほうは「読めなかったら金額を出さない」と正しく作ってあったのに、
**絵だけが 0円と言い切っていた**。言っていることが絵と字で食い違っていた。

しかも自分で報告に「絵は 0円と言い切ってしまう」と書いておきながら、
**「元の連なりから引き継いだ挙動なので変えていない」で済ませた。**

**対策** **読めていないことを、値0と同じ絵にしない**（水準の9）。
`null` は「0」ではなく「まだ分からない」。同じ面の中で、字が「出さない」なら
絵も「出さない」にそろえる。**引き継いだ挙動でも、嘘なら直す。**

直しかた: `unknown` を建ちぐあいの1つとして持ち、区画だけ取って
**建つものを薄く置く**（`docs/island-design.md` 4章の読み込み中の作り方）。
更地とも鉄筋とも見分けがつく。

### #22 章の名前を "use client" のファイルから持ち出して、表紙を丸ごと入れ替えていた（2026-09-10）

**何が起きたか** 「手で作った島が描いている章」の名前（ただの文字列）を
`components/isle/Cover.tsx`（"use client"）に置いて、サーバ側の `app/page.tsx`
から `import` して比べていた。クライアント側のモジュールの中身は、サーバから

**いつも false**。出発の日でもないのに、表紙が章の島に入れ替わっていた。

**なぜ気づけなかったか** 型は通る（`string` として通る）。ビルドも通る。
出来上がった島は「それらしく」見える。**性能を測ったら LCP が良くなっていた**ので、
危うく良い変更として報告するところだった。

**対策** **サーバとクライアントの両方が読む値は、どちらでもないファイルに置く**
（`components/isle/handmade.ts`）。そして、**画面の出し分けを入れたら、
出し分けの両側を DOM で数える。** 撮った絵だけでは「島が出ている」までしか
分からない。どちらの島が出ているかは、建っているものを数えると1回で分かる。

### #23 出発した次の日に「つぎの島」が消える作りのまま、出発前日まで来た（2026-09-10）

**言われたこと**「北欧周遊に明日からなると思うんですけど。なった時に、そして次の島が
ないと困ると思うんですよ。そのアルバニアに行った時にね。」

**原因** 島の連なりは「まだ始まっていない章」を次の島として出している
（`chapterNext()`）。章の表にあった未着手の章は北欧ひとつだけだったので、
**北欧が出発した瞬間に「つぎの島」が空になる**。しかも焼き込みのほうは
`CHAPTERS.find((c) => !c.from)!` で、`from` の空欄しか見ていないから
**北欧が「つぎの島」として自分を指す**。どちらも、出発の日を過ぎてみないと出てこない。

作ったときは、どちらも正しく動いていた。**間違っていたのは、日付で状態が変わるものを
「その日を過ぎた形」で見ていなかったこと。** 時計を1日進めて撮れば、前日に見つかる話ではなく、

- **`!` で型を黙らせない。** 無いことがありうるなら `undefined` を返し、
  受け取る側で決める。落ちない形にするなら、なぜその値で受けるのかを書き残す
- 章を足すのは当座しのぎ。**次の島を足し忘れても落ちない**ところまでやる

**外したのは、問いの立て方のほう。** 直せないのは*中身*であって、
**古くなったものをそのまま「いま」として出すかどうかは、こちらが決めること。**
しかもこの欄は 210〜280px の国旗で出していたので、**面でいちばん大きい絵が、

可能性がある。** 「人が書き替えるから大丈夫」は、書き替えられる人がいるときの話。

**対策**

- **人が手で書く欄には、「いつ書かれたか」と「いつまでなら本当か」をセットで見る。**
  `current.updatedAt` がいまの章より前なら、その場所はもう「いま」ではない

### #29 「今日」を UTC で切っている場所が1つだけ残っていた（2026-09-11）

**何が起きたか** 島の日付はほとんど日本時間で切っている（`lib/nightly.ts` の

`getUTCFullYear` / `getUTCMonth` / `getUTCDate` だった。UTC は9時間遅れなので、
**毎日 00:00〜09:00 JST のあいだ「今日」が前の日を指す。**

北欧への出発は 04:30 JST。**出発の瞬間から、まるごとその窓に入る。**
出発の夜の4時間半、表紙の「いま、いちばん近い企画」がいちばん大きい札で

（`NextUp.tsx` の一覧が、北欧を `daysLeft = -1` として落とすため）。
`/next` の先頭も `/now` の「次の企画まで 今日」も同じ。

**なぜ気づけなかったか** 日付の切り方が2つあることが、どこにも書いていなかった。

バグには見えない）。**ずれるのは1日のうち9時間だけ**なので、昼に撮っている
かぎり一生出てこない。出発の時刻が朝4時半だったのは、たまたま。

**対策**

- **日付の切り方は1か所に寄せる。** 島の「今日」は `lib/nightly.ts` の

- **日付で変わるものは、その日を過ぎた形で撮る**（#23 と同じ）。

  （`timezoneId: "Asia/Tokyo"`）。`Date` だけ差し替えて時差を UTC のままに
  すると、**JST と UTC の食い違いそのものが消えて、直っていないものが
  直って見える**。道具は `tools/sprites/jstday.mjs`
- 撮る時刻は**昼だけにしない。** 00:00〜09:00 JST の窓を必ず1本入れる

### #34 「読めなかった」を「無い」に倒して、旅先で島を動かせなくしていた（2026-09-10）

**言われたこと**「電波が細いと、あやとが島を動かせなくなる。今日いちばん重い1件。」
出発は翌日。**車の中・国境・山のなかからスマホ1台**で島を動かす旅で、
**電波が細いのは異常ではなく、ふつうの状態。**

**何が起きていたか** `POST /island-api/me` が**1回でも返らないと**、こうなった。
`abort` だけでなく **503 でも「45秒返さない」でも同じ**なので、
横取りの作りかたのせいではない（判定#13の裏取り済み）。

| 面 | 出ていたもの |
| --- | --- |
| `/me/desk` | 高さ 934px、「ここは、あやとの机」。**道具の札 0枚** |
| `/me` | 「島の手入れ」のカードごと消滅。**画面上に `/me/desk` へ行く道が1本も無い** |
| `/nordic/day/N` | 書く欄 1→0、書き出しの札 5→0、「入れる」消滅 |
| `/me` の数 | 付箋 20 / 企画 10 / カード 12 → **0 / 0 /（空）**＋「まだ1枚も貼っていません」 |
| `/me/remote` `/me/roulette` | **灰色の骨2本、998px。何分待っても変わらない** |

**しかも二度と読み直さなかった。** `lib/auth.tsx` の `token` は
`useCallback(…, [])` で参照が変わらず、読みにいく効果の依存が `[user, token]`
だったので、**画面を開き直すまで直らない。**

**原因** 3つとも根は1つで、**読めなかったことを「無い」と同じ絵にしていた**
（`docs/island-standards.md` 10）。

1. `amIOwner()` / `loadMe()` の `catch` が **`false` を返していた。**
   「読めなかった」は「あやとではない」ではない。しかも同じことを
   4か所（机・日誌・板・カード）がそれぞれ聞いていたので、
   **落ちたぶんの面だけが「あやとではない人」の顔に化けた**
2. 付箋・企画は `catch` で **`setStickies([])`** としていた。空の配列は
   「読めた上での0枚」のことばで、届かなかった日に言ってよい嘘ではない
3. 遠隔操作とルーレットは、`if (!ses) return <骨>` が**エラーの文言より上**に
   あった。文言（「開けませんでした。電波の届くところで、もう一度。」）は
   もう書いてあったのに、**構造上ぜったいに到達しなかった。**
   骨は「もうすぐ出る」の意味で、出ないものの上に置いてはいけない

**対策**

- **答えは3つ持つ。** `owner` は `"yes" / "no" / "unknown"`、読みものは
  `wait / ok / down`。**`unknown` は「オーナーである」でも「オーナーでない」
  でもない**ので、道具も出さないし、他人の顔にもしない
- **前に口が返した答えを、端末に覚えておく**（`ayato-island-owner`）。
  覚えているのは *口が返した答え* で、こちらで決めた答えではない。uid ごとに
  持ち、ログアウトで消える。実際に書けるかどうかは書く先の口
  （`functions/src/islandApi.ts` の `ownerUid`）がもう一度見ているので、
  ここを書き換えても道具は使えない
- **返事が来ないのも「読めなかった」**（`withRead`、12秒）。細い電波では
  断られるより固まるほうが多い。`fetch` は自分では諦めない
- **押されるまで待たない。** 落ちたら間隔を倍にしながら黙って読み直し、
  `online` と「画面に戻ってきた」でも読み直す。**画面を開き直させない**
- **島でひとつの答えを見る。** `POST /me` は `AuthProvider` が1回だけ引いて
  配る。面ごとに聞くと、落ちたぶんだけ答えが割れる

**確かめかた**（`tools/sprites/_read.mjs` / `readshot.mjs`）。
落とし方3通り（`abort` / `503` / 45秒返さない）× 端末2通り（前に読めたことが
ある / まっさら）× **視聴者さんでも同じ3通り**を撮る。
**7番目の条件がいちばん大事で、「読めなかったら見せる」に倒すと、
他人にオーナーの道具が見える。**

写真の骨 1 → **0** になる。


### #37 いま起きていること（旅）が、常設の入口ぜんぶの外にあった（2026-09-11）

**言われたこと**「いちばん見せたい `/nordic` が、常設4面から1本も辿れない」
「`/map` は『いまは北欧周遊のとちゅうです』と書いておきながら、そこへ行く
リンクを1本も持っていない」

**原因** 砂浜の一覧は `DOORS`（＝島に建っている10軒）から作っている。
**旅は建物ではないので、そこに入らない。** その結果、出発したあとの本番は
「伝説の企画」も「作った料理」も砂浜に並んでいるのに、**いま起きていることだけが
常設の外**にあった。実測で `/streams` `/about` `/apps` `/map` から `/nordic` への
リンクは0本。

#21 で言われた「常設は次の島でも引き継ぐ」は守れていた。**引き継ぐものの
一覧に、いま歩いている旅が入っていなかった**という、その裏返しを見ていない。

`/map` のほうは #12 とまったく同じ形。**名前を出しておいて、そこへ行けない。**
書いていないより悪い。

**対策**

- **常設の一覧は「建っているもの」だけで作らない。** いま起きていることは
  建物にならないので、別の口として先頭に足す（`content/trip.ts`）
- **日付で消えるものは、消える日を過ぎた形で撮る**（#23）。
  旅のあと（2026-09-30）に口が残っていれば、それは焼き込みで固まっている
- **章に旅の面が無ければ、口を出さない。** 行き先を作れば
  「これから建っていく島」の薄い1枚に着くだけ

### #38 「今夜」と名乗る2か所が、今夜の話をしていなかった（2026-09-11）

**言われたこと**「表紙の『今夜も22時から』の下に並ぶ配信2本が、3週間前と2ヶ月前」
「`/streams` の『今夜は、何をやってる日』に、今日を指す印がない。しかも日曜の列は
何も塗られていないので、見出しの問いに画面が答えていない」

**原因** 2つとも「**答えを持っているのに、別のものを出していた**」。

1. 表紙は `STREAM_TYPES[0].samples.slice(0, 2)`——**クッキング配信の代表として
   手で選んだ見本**——を出していた。見本は「その型がどんなものか」を見せるために
   選んであるので、新しい順ではない。直近5本は `/island-api/state` の
   `stats.latest` に毎晩入っていて、**同じページがもう読んでいた**
2. `/streams` は問いを見出しに立てておいて（`docs/island-design.md` 5-3）、
   下に出るのは1週間の回りかたの図だけだった。図から今夜を読むには、まず
   今日が何曜日かを自分で思い出すことになる。しかも**水曜と日曜はどの帯にも
   入っていない**ので、その2日は図を読んでも答えが無い

**対策**

- **見本と最新を、同じ場所で兼ねさせない。** 「今夜」と書いてある下に置くのは
  最新であって、代表ではない
- **問いを見出しにしたら、その場で字で答える。** 図は「だいたいこう回っている」
  を受け持つ。図から読み取らせるのは答えではない
- **本番の値を curl で見てから書く。** 型は `latest?: { videoId: ... }` と
  書いてあったが、**本番はずっと `video_id` を返していた**
  （`python/island_daily_stats.py` の `SELECT AS STRUCT video_id`）。
  誰も読んでいなかったので気づかれず、そのまま読んでいたら動画IDが
  `undefined` のサムネイルを2枚並べるところだった

**ついでに見つかったもの。** 今日の列を通して初めて、`/streams` の週の帯が
**曜日の見出しと最大12pxずれていた**ことが見えた。7つのマスを自動で置いていたので、
色の帯が先に列を押さえた行では、余ったマスが8列目・9列目にこぼれて7列が痩せていた。
**まっすぐな線を1本引くと、揃っていないものが見える。**
