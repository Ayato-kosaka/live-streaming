# 何が機械で新しくなり、何が人しか新しくできないか

島に出ている数字と言葉は、`site/content/*.ts` に**焼き込んである**。
配り直しても動かない（Hosting の `npm run build:web` は python を1行も通らない）。
だから「新しくする」は**焼き直して commit する**ことを指す。

ここに書くのは**その仕分けだけ**。何をいつやるかの手順は `/island-fresh` にある。

**焼き込みでないものは、ここには載っていない。** 投げ銭の台帳（`islandTips`）と
カード（`islandCards`）は Firestore に置いてあって、画面は**出すたびに読み直す**
（`functions/src/cards.ts`）。焼き直しも配り直しも要らない。
代わりに「**いつ台帳に入るか**」が要るので、それは
[`island-db.md`](./island-db.md) の 5.1「台帳とカードは、いつ入るか」に書いてある。

---

## 1. 仕分けの軸は「本番を読めば答えが出るか」

| | 答えの出どころ | 誰が新しくするか |
| --- | --- | --- |
| **① 機械だけで決まる** | 本番（BigQuery / Firestore）だけ | 毎晩ひとりでに焼く |
| **①b 焼けるが、上流が人** | 本番 ＋ **リポジトリの中の**人の書いた表 | 人が上流を書いたあと、続けて焼く |
| **② 人しか決められない** | 人の頭の中 | 人が書く。機械に決めさせると嘘になる |

**軸は「BigQuery か」ではなく「本番か」。** Firestore の中身（キャラクターの
名簿など）も、あやとが画面から足せば勝手に増えるので、こちらが何も書かなくても
新しくなる。そこを「人の書いた表」と同じ扱いにすると、**本番では増えているのに
焼き込みだけが何か月も止まる。**

**もう一度止まった（2026-09-17）。** `shorts.ts` は「BigQuery にショートが
1本も入っていないから、人しか焼けない」として②に置いてあった。前半は本当で、
**後半が間違っていた。** 公開のチャンネルのショートのタブは鍵なしで読めるので、
本番を読めば答えが出る。②に置いてあったあいだ、棚は **2026-05-12 から127日**
止まり、いちばん自慢していい時期（イランまで歩いたあと、北欧へ出るまで）の
ショートが25本、棚に無かった。**「BigQuery に無い」は「機械では取れない」ではない。**

**実際に止まった（2026-09-15）。** `residents.ts` は「BigQuery だけ」の①に
置いてあったが、島を歩く候補は `python/residents_map.json`（リポジトリの中の
手書き22行）が決めていた。#284 でキャラクターを Firestore に移したあとも
そちらだけが取り残されて、**名簿の102人のうち80人が一度も島に立てなかった。**
毎晩緑が付いていたので、止まっていることが誰にも見えなかった。

**①b を毎晩に入れない理由**は、入れても変わらないからではなく、
**変わらないのに緑が付く**から。「今日も回った」が並ぶと、上流（`countries.ts` など）が
止まっていることが隠れる。動かないものを動かしても、止まっていることは直らない。

**ただし「上流が人」だけでは外す理由にならない**（2026-09-10）。見るのは
**上流が止まっているあいだ、下流も止まるか**。`cityStreams.ts` は止まらない——
街の一覧が増えなくても、いまいる街の配信は毎晩増える——ので、①に上げた。
下の3章に、外に置いたままの3本との違いを書いてある。

## 2. ① 機械だけで決まる — 毎晩ひとりでに焼く

`.github/workflows/rebake.yml` が **01:00 UTC**（日本時間の朝10時ごろ）に回す。
取り込みの実測が 21:49〜23:32 UTC なので、その後ろに置いてある。
変わっていれば master に入れて、Hosting も配る。

| 焼くもの | スクリプト | 何が変わると動くか |
| --- | --- | --- |
| `chapterStats.ts` `chapterStreams.ts` | `build_chapter_stats.py` | 配信が増える／章が閉じる／**名簿に人が増える** |
| `residents.ts` | `build_residents.py` | 直近90日が1日ずれる（**毎日動く**）／**名簿に人が増える** |
| `streamPeaks.ts` | `build_stream_peaks.py` | 取り込めた配信が増える |
| `onThisDay.ts` | `build_on_this_day.py` | 配信が増える |
| `cityStreams.ts` | `build_city_streams.py` | 配信が増える（街の一覧が増えるのは人待ち） |
| `countryStats.ts` | `build_country_stats.py` | 配信が増える（国の一覧が増えるのは人待ち） |
| `shorts.ts` | `build_shorts.py` | **あやとがショートを出す**（YouTube を読む。BigQuery ではない） |

**上から4本目までは入力が本番だけ。** 人がリポジトリに何も書かなくても正しい答えが出る。

**焼き込みでないものが1つだけ、同じ晩に入っている。** 分かち合う1枚
（`site/public/og.png`）で、リンクを貼ったときに出るあの絵。中の言葉は全部
「画面が出しているもの」を撮っただけなので、**撮り直せば正しくなる**——のだが、
撮り直す人がいなかった（`island-misses.md` #134）。いまは `tools/sprites/ognight.sh`
が毎晩、書き出したものを静的に配って撮り直す。

**絵のバイト列では見ない。** 住人が歩き波が動くので、同じ入力でも撮るたび
3.8〜4.6% の画素が入れ替わる。見るのは**絵に写るべき字**（島・看板・帯・
旅のしるべ・島の札）で、いま配ってあるぶんが `tools/sprites/og-stamp.json`。
字が変わった晩だけ絵を差し替えて、その晩の commit に一緒に乗せる。

撮れなかった晩は**絵を据え置いて、数字は配る**（絵が古いのと数字が古いのは
別の話）。黙りはしないので、deploy のうしろで run が赤くなる。

いちばん上の2本は **BigQuery と Firestore の両方**を読む。

| 何を | どこから |
| --- | --- |
| 島を歩く候補（絵と絵文字） | Firestore `islandCharacter`（あやとが画面から足す） |
| 一緒にいた日数 | BigQuery `chat_messages`（直近90日の出席） |
| どの絵が誰か | **名簿の `lookupKeys` に、チャットの名乗りを当てる**（カードの絵と同じ道） |

結ぶところは `python/build_residents.py` の `link()` **1か所だけ**が持っていて、
`build_chapter_stats.py` もそこを呼ぶ。2か所で結ぶと、島と連なりで別の絵が出る。

**決められないものは結ばない。** 同じ鍵が2人に付いているとき、1つの絵に2つの
チャンネルが当たるときは、どちらも候補に入れない。当てずっぽうで立たせると
**別人の絵が島を歩く。** 逆に、名乗りが誰とも当たらない人は候補に入る
（`days` が 0 になるだけで、絵は立つ）。結べないことと、絵が無いことは別のもの。

`cityStreams.ts` と `countryStats.ts` は上流に人の書く `countries.ts` がある。それでも
毎晩に入れたのは、**上流が止まっても下流が止まらない**から。街や国の一覧が増えなくても、
配信が増えればトビリシもカズベキも増える。

**そして旅のあいだは、上流そのものが別にある**（2026-09-16）。`countries.ts` は
旅から帰った本人が書く表なので、旅に出ているあいだは1行も増えない。
いま歩いている旅の滞在は `content/nordic.ts` の旅程（出発前に確定している）から出す。
2つを足して「その日どこにいたか」を答えるのが `python/stays.py` で、
**この2本と `build_on_this_day.py` は、そこだけを読む**（`countries.ts` を
それぞれの正規表現で読むのをやめた。同じ読み落としを2回踏んだため）。

**旅程は予定なので、今日より先は滞在に入れない。** 入れると9日後のストックホルムが
「歩いた国」に立ち、街の欄が先にできて「配信はのこっていない」と言い出す。

**そして、入れなかったからこそ嘘が半年残った**（2026-09-10）。
一度も焼き直されないまま手で書いたものが置かれていて、**36街89本**しか入っておらず、
拾えていない街が画面で「配信はのこっていない」を名乗っていた。焼き直して**49街322本**。
`docs/island-misses.md` #12 に経緯がある。

**`shorts.ts` だけは BigQuery も Firestore も引かない。** 読むのはチャンネルの
ショートのタブ（`https://www.youtube.com/channel/<id>/shorts`）で、鍵は要らない。
1ページ目だけでは全部にならないので、続き（`continuationCommand` →
`POST /youtubei/v1/browse`）まで追う。題名は一覧から取れるので、1本ずつ開くのは
**公開日の要るもの＝手元にまだ無いものだけ**。章の割り当ては**公開日だけ**で決める
（題名の街名では決められない。ロンドンは2回ある）。

**走者から届くことは、毎晩に入れる前に実測した**（2026-09-17）。この箱は出口の IP を
他と共有していて、視聴ページを数十回開くと 429（reCAPTCHA の頁）が返る。
**手元で届くことは、走者で届くことの証明にならない。**

`build_on_this_day` は `streamPeaks.ts` を読むので、**`build_stream_peaks` のあと**に回す。
順番はワークフロー側で固定してある（入力の並びではなく allowlist の並びで回る）。

### 毎晩ひとりでに回すものには、止め金がいる

`ACTIVE_FRIENDS`（直近90日の常連の数）が **61 → 174** になったことがある。
読めなかった日を全員の出席に足していたので、1回来ただけの人が72人まぎれ込んだ
（`python/build_residents.py` の docstring に実測が残っている）。
**あのときは目で見て止めた。毎晩ひとりでに回すなら、その目はいない。**

いま止め金は3つある。**前の3つは commit の前**に効いて、悪いものを入れさせない。

1. **焼いた結果が、焼く前より縮んでいたら落とす**（`rebake.yml` の
   「中の数が縮んでいないか」）。毎晩焼くものぜんぶが対象
2. **焼いた TS で `next build` が通らなければ落とす。**
   通らないまま入れると、赤くなるのは master ではなく**次の Hosting のデプロイ**で、
   次に誰かが配るまで誰も気づかない
3. **`countries.ts` の滞在を1件でも読み落としたら落とす**（`python/stays.py` の
   `read_countries()`。**ここだけが `countries.ts` を正規表現で読む**）。
   読み落としは例外を出さず、**国と街が黙って減るだけ**だった。減った街は画面で
   「配信はのこっていない」と言い切るので、**落ちて赤くなるほうがずっといい**

もう1つ、**時間の軸で見るものが commit の後ろにある**（`rebake.yml` の
「凍っていないか」）。

4. **焼き直したのに中身が何日も同じなら、run を赤くする。**
   緑は「回した」としか言っていない。上の3つは**焼く前と焼いた後**を比べるので、
   凍っているものはその2つが同じで何も起きない。見るのは「前に中身が変わってから
   何日たったか」で、日数はファイルごとに置いてある（**0 は「見ない」**）。
   **ここでは commit を止めない。** 凍っているときに入れるものは1バイトも無いし、
   同じ晩に動いた他の焼き込みまで道連れになる。焼けたものは入れて配ってから、
   run のいちばん最後で赤くする。
   - **「焼いた日」は中身に数えない。** `chapterStats.ts` は冒頭に
     「数えた日: YYYY-MM-DD」を書くので、そのまま比べると数字が1つも動いていない晩まで
     「変わった」と読める
   - **変わらなくて正常なものは見ない。** `chapterStreams.ts`（章が閉じるまで動かない）、
     `kitchenTalk.ts`（上流が人）、`shorts.ts`（あやとが出した晩だけ動く。
     4ヶ月出ない期間が実際にある）。狼少年にしたら、次からは誰も読まない

### 赤は、誰も見ていない

**止め金が4つとも効いても、赤くなるだけでは誰にも届かない。**
2026-09-16 の焼き直しは TypeError で2秒で落ちて（`island-misses.md` #105）、
同じ日にもう1回落ちて、**そのあいだ issue は1本も立っていない。**
見つかったのはこちらがたまたま Actions を見に行ったからで、仕組みではなかった。

赤は Actions の一覧の中にしか出ないうえ、**「起きたこと」であって「いま残っていること」
ではない。** 次の晩に緑が積まれれば下へ流れていく。

だから、**いまの状態そのものを issue の一覧に置く**（`.github/workflows/bake_down.yml` と
`python/bake_down.py`。`ingest_down.yml` が Doneru の取り込みでやっているのと同じ形）。
焼き直しが新しくなっていないあいだ **issue を1本だけ開き続け、また焼けたら自分で閉じる。**
上の2通り（**焼くのが落ちた** ／ **凍っていた**）は直し方が違うので、**本文で書き分ける。**

**凍っているかどうかを、見張りはもう一度判定しない。** ここに書いてある日数と
step「凍っていないか」の判定が正で、見張りが読むのは**「凍っていたら赤くする」という
step が落ちたかどうか**だけ。しきい値を2か所に置くと、片方を直し忘れた日に食い違う。

**数えるのは無人で走ったぶんだけ**（cron と `workflow_run`）。手で押した run は
押した人がその場で見ているし、手押しの既定は `dry_run: true` で**通っても master には
1バイトも入らない。** そこを緑として読むと、止まっているのに issue を閉じる。
**ただし赤いあとで手で押して通っていたら、その朝は判断を保留する**（開きも閉じもしない）。
手押しでも `焼く` も `凍っていないか` も同じように通るので、そこが緑なら焼くのはもう直っている。
直した直後に「止まっています」と言わないため。

### 1つめが何を見ているか（と、しきい値の根拠）

**焼き込みはほぼ全部が累積**（配信は増えるだけ）なので、正常な晩の動きは
「増える」か「動かない」しかない。**だから見るのは縮みだけで、増えるほうは止めない。**
縮む理由は2つしかなく、どちらも量が違う。

| 縮む理由 | どれくらい縮むか |
| --- | --- |
| 動画が1本非公開になった／取り込み直しで境目の値が動いた | **1〜数件**（0.1〜1%） |
| 塊が落ちた（国ひとつ・章ひとつを読み落とした） | **数十%** |

しきい値はこの2つのあいだに置く。累積の数は **0.9〜0.95倍**（実測した塊の大きさ:
`chapterStats` の最小の章は 6.3%、`cityStreams` のジョージアは街の14%・配信の16%、
`onThisDay` のジョージアは 61%）。窓で切っている `residents.ts` だけは正常でも
上下するので、`ACTIVE_FRIENDS` は**上にも下にも 1.5倍**の幅で見る
（61 → 174 が止まる幅。2026-09-10 の本番の実測は 57 なので、いまの値でも鳴らない）。

**それとは別に、比率では測れない2つを見る。**

- **章・国の数は、1つでも減ったら止める。** これは人が書いた表（`chapters.ts` /
  `countries.ts`）から来る数で、**読み落とし以外では減らない。** 量でも測れない:
  `cityStreams` のいちばん小さい国はオランダの配信1本（0.3%）で、
  比率のしきい値をどう置いても引っかからない
- **「中身が埋まっている割合」を見る。件数だけでは足りない。**
  2026-09-10 に `read_countries()` がジョージアを落としかけたとき、
  `onThisDay.ts` の**件数は1件も減らなかった**（`place_of()` が `("", "")` を
  返すだけ）。減ったのは「場所の字が入っている割合」で、99.8% → 38.5%。
  同じ形の壊れかた（本数はそのままで題名だけ空、住人はそのままで絵だけ空）が
  ほかのファイルにもあるので、**焼くものすべてに1つずつ置いてある**

**上流のスクリプトの中にも止め金があるが、二重ではない。層が違う。**
スクリプトの中（`read_countries()` / `read_stays()`）は**「入力を読み落とした」**を、
ワークフローは**「出力がやせた」**を捕まえる。入力の読み落としは表の書き方が
変わるたびに新しい抜け道ができるので、**出口でもう一度、数で見る。**
上流が完璧なら、ワークフローの止め金は一生鳴らない。それでよい。

**Firestore を読む2本には、そのぶんの止め金が中に要る。** 名簿が1人も返らなかった
とき、そのまま焼くと**島から人が消える**——それは「今日は誰も来ていない」と同じ絵に
なる（`docs/island-standards.md` 10）。だから `build_residents.py` は
名簿が空／読めないときは `residents.ts` に1バイトも書かずに 1 で終わり、
`build_chapter_stats.py` も同じところで止まる。

**ワークフローの止め金では捕まえられない。** あちらが見るのは「縮んだか」で、
名簿が読めなかった晩は**縮むのではなく、まるごと空**になる。空になったものは
0.9倍にも 1/1.5 倍にもならない。だから**スクリプトの中で落とす。**

（2026-09-15 に手書きの表を切ったので、`residents.ts` の住人は 22 → 名簿の人数へ
**一度だけ跳ねる。** ワークフローの止め金は縮みしか見ないので、増えるほうは通る。）

## 3. ①b 焼けるが、上流が人 — 人が書いたあとに、続けて焼く

| 焼くもの | スクリプト | 待っているもの |
| --- | --- | --- |
| `kitchenTalk.ts` | `build_kitchen_talk.py` | `recipes.ts` と、手で選んだ引用 |
| `legendDays.ts` | `build_legend_days.py` | `legends.ts` に足された伝説 |

**上流が止まっていれば、下流も止まる。** `recipes.ts` の料理名も `legends.ts` の
「どれを伝説と呼ぶか」も、人しか決められない。そこが増えるまで下流も動かない。

**この2本は BigQuery を引かない。** ここが `cityStreams.ts` との違いで、
毎晩に入れなかった理由でもある。

| | BigQuery を引くか | 引かないなら、元は何か |
| --- | --- | --- |
| `build_kitchen_talk` | **引かない** | `python/data/kitchen_*.json`（3つ） |
| `build_legend_days` | **引かない**（`bigquery` を import すらしていない） | `python/data/legend_*.json`（2つ） |

**`build_country_stats` はここから①へ移した**（2026-09-16）。頭に
「BigQuery から焼く」と書いてあったのに、置いてあった SQL はどこからも
組み立てられておらず、実際は `python/data/country_stats.json` を焼き直すだけだった。
その取り置きは **2026-05-06 で止まったまま4ヶ月**、毎晩緑のまま誰にも気づかれず、
表紙も住人も「17カ国を歩いた」と言い続けた。いまは滞在から SQL を組んで引く。
JSON は**引いた結果の写し**として置き直すだけで、もう入力ではない。

**先にその JSON を取り直さないと、回しても同じものが焼き直るだけ。**
取り直す SQL は各スクリプトの `--sql` が出す。だから毎晩に入れると、
本当に「変わらないのに緑が付く」ことになる。

（`cityStreams.ts` は 2026-09-10 に①へ移した。上の2章。）

## 4. ② 人しか決められない — 機械に決めさせると嘘になる

| 何 | なぜ機械にできないか |
| --- | --- |
| `recipes.ts` | 料理名・種類（7種）・**スタンプの絵を `food-*` 105枚から1枚選ぶ**。しかも同じ絵を2品で使わない。配信の題名から料理名は決まらない（「北欧旅まであと２日！トトロクッキング！」） |
| `kitchenTalk.ts` の `talk` | 引用を手で選ぶ（`python/kitchen_talk_picks.json`）。機械だと「こんばんは」が並ぶ |
| `voices.ts` | 他己紹介の抜粋を手で選ぶ（`python/voices_picks.json`） |
| `countries.ts` | 歩いた国と滞在期間。本人しか知らない |
| `chapters.ts` | 章（島）の区切り |
| `legends.ts` | どれを伝説と呼ぶか |
| `plans.ts` `apps.ts` | 企画・アプリの選定 |
| `voice.ts` `chatter.ts` `site.ts` `themes.ts` `directory.ts` | 画面に出る言葉 |
| `aboutWords.ts`、`nordic.ts` の `WHY` `THEMES` `THEME_WORD` `UNPLANNED` `THANKS` | **本人が書いた文そのもの。** 本人が書かないかぎり増えない |

**「選ぶ」が入っているものは、全部ここ。** 数える・並べる・絞るは機械にできるが、
**どれを載せるかは載せる理由がいる。** 理由は BigQuery に入っていない。

### 本人の言葉には、書かれた日をいっしょに置く

`site/content/aboutWords.ts` は、2026年9月11日（海外に出て丸二年）の投稿から
そのまま引いてある。**1字も直さない**ので、中に「1万インストール」「食べログまであと4位」
のような**そのうち古くなる数字**が入っている。

古くならないのは、**その日に本人が言ったこととして出しているから**。
`/about` の見出しの下に「2026年9月11日、海外に出て丸二年の日に、本人が書いたもの。」が
必ず出ている。**この文を、日付から切り離して他の面へ持っていってはいけない。**
切り離した瞬間、来月には嘘になる（`docs/island-standards.md` 8章と同じ理由で、
手で書いた数字は片方だけ古くなる）。

数字だけを最新に保ちたくなったら、**本人の文を書き換えるのではなく、
その数を持っている面（`/apps`）に新しい節目を1行足す。** 引用は引用のまま置く。

### 機械にやらせて壊れたところ

`recipes.ts` の `icon` には「同じ絵を2品で使わない」という決まりがある。
スタンプ帳は**押した数だけ違う絵が並ぶ**から図鑑に見える。同じ皿が2つ並んだ瞬間、
絵ではなく飾りになる。105枚あるので使い回す理由もない。
**この「2度使わない」は、料理名からは導けない。**

## 4b. ③ 外の地図から来るもの — こちらの都合では変わらない

旅の面には、BigQuery でも人の頭でもなく、**外の地図（OpenStreetMap）**から
焼いたものが3つある。

| 焼くもの | スクリプト | 何が変わると動くか |
| --- | --- | --- |
| `nordic/citymaps.json` ＋ `public/nordic/city/*.svg` | `tools/nordic/citymap.py` | OSM に道・建物が足される |
| `nordic/geo.json` | `tools/nordic/geocode.py` | 見どころが増える |
| `nordic/shops.json` | `tools/nordic/shops.py` | **街の店が開く・閉まる**（`docs/nordic-shops.md`） |

**毎晩に入れない。** 相手は公共の無料サーバで、こちらが毎晩叩いてよいものではないし、
街の店は1日で変わらない。**旅程に街が増えたときと、街の様子が古いと分かったときだけ**回す。

止め金の考え方は2章と同じだが、見るところが違う。
**0軒と「読めなかった」を分ける**のがここの要（`docs/island-misses.md` #79）。
Overpass は混むと空を返すので、失敗を 0 として焼くと、画面が「この街には無い」と
言い切ることになる。`shops.py` は読めなかった街について
**前に読めた表をそのまま残す。**

`site/content/*.ts` は **35本**ある（2026-09-17 の実測。それまでここには数を

### 日付は、コメントから拾わない

`site/content/*.ts` にはコメントにも日付が書いてある（`characterBox.ts` の
「あやと『大きさも不揃い』2026-09-10」など）。**あれは中身ではない。**
とくに `chapterStats.ts` / `chapterStreams.ts` の冒頭の「数えた日:」は
**焼くたびに今日になる**ので、拾うと中の数字が半年止まっていても新しく見える。

だから拾うのは **`"…"` の中に在る日付だけ。** 注釈を先に落とすのは
`island-misses.md` #125 の決めごと2と同じ形。

### 4つの見かた

| 見かた | 何が起きたら赤いか | 付けた本 |
| --- | --- | --- |
| `LATEST` | 中の**いちばん新しい過去の日付**が、今日から `days` 日より前 | 増えていくもの（12本） |
| `COVERS` | 中の**いちばん先の日付**が、もう今日に届いていない | 先ぶんの表（2本） |
| `KEYS` | **上流の鍵が、下流に無い**（1件でも） | 上流が人・名簿の3本 |
| `SHARE` | 上流の鍵のうち**下流に無いものの割合**が超えた | セリフ（1本） |

`KEYS` と `SHARE` を分けてあるのは、**「1件も欠けてはいけない」と「欠けていて
当たり前」を同じ判定にすると、後者が永遠に赤いまま誰にも読まれなくなる**から。

`KEYS` を足したのは `kitchenTalk.ts` のため。あれは**日付を1つも持っていない**ので、
日で測ろうとすると一生鳴れない。見るべきは「`recipes.ts` に在る品が焼かれているか」で、
これは人が上流を書いた翌日から赤くなってほしい（猶予を置いていない）。

## 4. 画面の字が、いつ嘘になるか（`python/text_expires_watch.py`）

**軸が3本目。** 上の2つは「焼き込みが古いか」を見るが、こちらは
**画面に出る文が、ある日に嘘になるか**を見る。

```bash
python3 python/text_expires_watch.py              # 0=通った / 1=見つかった / 2=数えるものが無い
python3 python/text_expires_watch.py --dir 写し --today 2026-09-17
python3 python/text_expires_watch_selftest.py     # 対照（29件）。0=通った / 1=外した / 2=対照0件
```

**`rebake.yml` にはまだ繋いでいない**（2026-09-17。あの回は別の担当が触っていた）。
繋ぐときは、上の対照を `run:` に1行足して、そのあとに本体を回す。

| | 何を見るか | どこを読むか |
| --- | --- | --- |
| 凍り（`rebake.yml`） | 焼き直したのに字面が動かない | git の履歴 |
| `stale_content_watch.py` | 焼き込みの中の日付が今日から離れた | `site/content/*.ts` |
| ここ | **画面の文が、ある日に嘘になる** | `site/app` `site/content` `site/components` |

### 拾うものの決めかた

**1件ごとに「いつ嘘になるか」を言えること。** 言えないものは拾わない。
これが唯一の歯止めで、これが無いと「なんとなく古そう」が何十件も並んで、
誰も読まなくなる（`island-standards.md` §15）。

日付は3通りで読む——文の中の日付／同じ文の中で**月を持ち回った日**／
企画のように**すぐ上の欄（`date:` `until:`）にしか日が無い**もの。
そのうえで「これから起きる言い方」（`FORWARD`）が同じ文にあるものだけを拾う。
**丁寧形（〜ます）は入れない**——「城があります」はいつ読んでも本当。

**過去の事実は拾わない。**「2023年8月1日に出会った」は日付があっても通る。
判定しない本（視聴者さんの書き込みと配信の題名）は `QUOTES` に並べて、
**中身は出さずに数だけ**表に出す。

### 2026-09-17 の実測

250本 / 画面に出る字 7,473件（うち日付を持つ 115件。50件は上の欄から日を取った）を見て、
直したのが **10件**、嘘にならないと決めたのが **2件**（`ALLOW` に理由つき）。
