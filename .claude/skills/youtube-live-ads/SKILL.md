# ライブアーカイブの広告をオンにする

**Studio の触り方は `youtube-studio` に、EC2 の触り方は `ec2-chrome` に書いてある。** ここは見回りの手順だけ。

## 0. 何をする見回りか

あやと（2026-10-09）:

> 対応する → 曲を消去する → … → 保存。そうすると「動画編集が進行中です...」となるので、一旦OK。
> 対応中のものはリポジトリの何処かにメモする。次回からは、対応中のものが解消されていれば収益化をオンにして、
> まだ申立があれば再度対応をする。ライブ配信の日付が一番見たものの中で最新を記録しておけば、
> 次回からは差分のライブ配信の動画を確認する。

決まったこと（#757、あやと 2026-10-12）:

- **対応は「曲を消去する」（曲だけを消し、会話などの音は残す）。区間を全部ミュートはしない。**
  はじめの仕様はミュートだったが、あやとが「間違っていた」と直した。ミュートで済ませた
  hK0SwIeAxg0 は元に戻せないのでそのまま
- 申し立てが無いのに収益化がオフの動画は、オンにする（Q1: A）
- 権利者と収益を分け合っている動画も、申し立てを消して全額に戻す（Q2: B）

聞いていること（#757 Q4）: 「曲を消去する」が選べない申し立て（一致した箇所が多すぎる／作曲への申し立て）を
ミュートするか。答えが来るまで `manual` に積む

## 1. 台帳（`ledger.json`）

| キー | 中身 |
| --- | --- |
| `checked_through` | 見た中でいちばん新しい配信（開始時刻・id）。次回はこれより新しいもの＋その前14日ぶんを見る |
| `hold` | 手を付けない動画と、その理由（`#757 Q4 の答え待ち` など）。id → 理由 |
| `videos` | **片づいていない動画だけ。** 収益化されたら消える |
| `videos.*.state` | 下の表のどれか |
| `videos.*.history` | 送った対応（日付・申し立て・曲・`erase` か `mute`。ミュートなら区間の秒） |

**台帳はこのリポジトリの中に置く**（期限や状態を持つが、見回りの道具が毎回読み書きする入力なので、
`docs/` ではなくスキルの横）。あやとが見たいときは issue ではなくこのファイルを見ればよい。

## 2. 手順

```bash
E=.claude/skills/ec2-chrome/ec2.py
python3 $E put .claude/skills/ec2-chrome/cdp.py /home/ubuntu/cdp/cdp.py
python3 $E put .claude/skills/youtube-studio/yt_studio.py /home/ubuntu/cdp/yt_studio.py
python3 $E put .claude/skills/youtube-live-ads/live_ads.py /home/ubuntu/cdp/live_ads.py
python3 $E put .claude/skills/youtube-live-ads/ledger.json /home/ubuntu/cdp/ledger.json
```

1. **まず `--dry`。** 何も送らず振り分けだけを出す:
   `cd /home/ubuntu/cdp && timeout 280 python3 live_ads.py ledger.json /home/ubuntu/shots/ledger.dry.json --dry`
2. 振り分けを読む（`ledger.dry.json.log.json`）。`to-erase` の本数と曲が妥当か、`manual` が無いかを見る
3. 本番。**1本につき画面を押すので90秒ほどかかる**（`resolve_claim_ui`）。50本なら1時間を超え、
   SSM の1回（600秒）に収まらないので、EC2 の上で切り離して流す:
   ```sh
   cd /home/ubuntu/cdp && setsid nohup /usr/local/sbin/ec2-queue hold ytstudio --who live-ads --purpose '曲の消去の一括' -- \
     python3 live_ads.py ledger.json /home/ubuntu/shots/ledger.out.json > /home/ubuntu/shots/out.log 2>&1 < /dev/null &
   ```
   列 `ytstudio` の札を一括の pid で持つ（`ec2-chrome` 2.5）。ほかの人が Studio の Chrome を持っていれば空くまで待ち、
   一括が終われば札も消える。見張り（idle-stop）は札を見て止めない
   進み具合は `ledger.out.json.progress`（1本1行）を `wc -l` で見る。終わると `out.log` に件数が出る。
   **曲の消去は元に戻せない。** 何本に送るかを、流す前にあやとへ一言添える
4. `ec2.py get` で `ledger.out.json` を持ち帰り、`ledger.json` に上書きしてコミット
5. 1本、`url_of("video/<id>/claims")` を `shot` して「動画編集が進行中です…」を目で見る

## 3. 振り分け（`live_ads.py` の `classify`）

| state | いまの状態 | すること |
| --- | --- | --- |
| `done` | 収益化されている | 台帳から消す |
| `editing` | 動画編集が進行中 | 待つ。次回また見る |
| `erase` → `editing` | 申し立てがあり、「曲を消去する」が選べる | **1件だけ**送る。残りは次回 |
| `to-erase` | （`--dry` のとき）上と同じ | 次の本番で送る |
| `enable` | 申し立てが無いのに収益化がオフ | 収益化をオンにする（下の4章） |
| `hold` | `hold` に載っている | 何もしない |
| `manual` | 「曲を消去する」が選べない申し立て、または申し立て以外の理由 | 人が見る。issue にする |
| `error` | 送ったが失敗した | 理由を読んで次回やり直す |

**1本に申し立てが何件あっても、1回の見回りで送るのは1件。** 編集中は次の申し立てに触れないから
（画面の「対応する」も押せなくなる）。2026-10-10 時点で、1本に複数件ついている動画は34本、最多は35件。

## 4. まだ分かっていないこと

- **申し立てが解けた動画は、収益化がひとりでにオンに戻る。** 申し立てが付いているあいだ、Studio は
  スイッチを `OFF` と返すが、解けると `ON` / `MONETIZING` になる。こちらで押す必要は無い
  （hK0SwIeAxg0 で確かめた。04:38 UTC に送り、06:57 UTC には申し立てが消えて「この動画は設定どおりに
  収益化されています」になっていた。**編集は2時間20分以内に終わる**。3時間30分の配信・31秒のミュート）。
  終わった直後は `inlineEditProcessingStatus` が `PROCESSING_NON_PRIMARY_ASSETS` になるが、これは編集中ではない
- **収益化をオンにする操作は、このセッションの安全判定に止められる**（2026-10-12、理由は「お金に関わる現実の操作」）。
  画面の形だけは分かっている: `/video/<id>/monetization/ads` の「オフ」の欄（`ytcp-video-monetization #container`）を
  押すと `ytcp-video-monetization-edit-dialog` が開き、ラジオ「オン／オフ」と「完了」が出る。完了 → 右上の「保存」。
  保存が送る要求はまだ写していない。許可が出たら `capture(t, act=…)` で写して `enable_ads()` を足す。
  それまで `enable` は台帳に積むだけで、あやとに Studio の一括編集でオンにしてもらう
- **「曲を消去する」が選べない申し立てがある。** `claimResolutionEligibility.waveformEraseEligibility` が
  `TOO_MANY_MATCHES_PER_CLAIM`（1件の申し立てに一致した箇所が多すぎる）か `COMPOSITION_CLAIM`
  （録音ではなく作曲への申し立て。カバー曲など）のとき。ミュートは選べる（#757 Q4）
- **「曲を消去する」で申し立てが消えても、収益化はオフのまま残る**（2026-10-12、DPVX8gBosWM・6_2Pw1uIDqI ほか6本）。
  ミュートで片づけた hK0SwIeAxg0 はひとりでにオンに戻ったが、曲の消去のほうは戻らなかった。
  なので、片づいた動画も `enable`（収益化をオンにする）に回る
- **曲を消したあと、しばらく「申し立てを再処理中」になる**（`waveformEraseEligibility` が `…CLAIMS_BEING_REPROCESSED`）。
  このあいだは次の対応を選べない。`editing` として待つ
- **録音への申し立てを消すと、作曲への申し立てだけが残ることがある**（kunXt2sXnFQ は6件残った）。
  そのときは収益を分け合う形（`MONETIZING_WITH_REVSHARE`）で収益化が戻る。作曲への申し立ては曲の消去では消せない
- **「曲を消去する」は早い。** d2q2XuA7ss0（6時間の配信）は、2026-10-12 00:30 UTC ごろに送って、
  00:47 には申し立てが消えて収益化されていた（17分以内）
- **編集を続けて送ると、Google の「本人確認」が出る**（2026-10-12 07:40 UTC、その日67件目のあたり）。
  「対応する」を押すと「操作を選択」ではなく「本人確認：続行するには、本人確認を行う必要があります」が出て、
  以後は全部 `timeout: …ytcp-dialog…` で落ちる。パスワードかスマホの確認が要るので、あやとに通してもらう（#768）。
  1日に送る数を絞る。**本人確認を通したあとも、同じ日に続けると1時間ほどでまたログインが切れた**
  （2026-10-12 は 01:30 と 09:00 の2回、3アカウントとも Signed out）。半日で70件近く送った日だった。
  **1回の見回りは10件まで、1日1回**にする（`live_ads.py --max 10`）
- **途中でログインが切れたら、すぐ止める。** Studio が 401 を返し始めると、以後は全部 `ytcfg` が無いで落ちる
  （2026-10-12 に50本ぶん空振りした。#768）。`live_ads.py` は落ちた動画を台帳に残すので、ログインし直してから
  同じコマンドを流し直せば続きから進む
- **配信の数日後に付く申し立て。** 前回より14日さかのぼって見直しているが、それより後に付いたものは拾えない。
  ときどき `--all` で全件を見る

## 4.5 収益化をオンにするのは、あやとが Studio で一括で押す

このセッションからは、収益化をオンにする操作（1本ずつも、一括編集を開くところも）が安全判定で止められる
（2026-10-12、理由は「お金に関わる現実の操作」）。なので `enable` がたまったら、#757 の手順で
あやとに一括でオンにしてもらう。**絞り込み「収益化対象外」は、スイッチがオフなだけの動画を全部は拾わない**
（2026-10-12 に一括でオンにしてもらって、43本は戻り35本が残った）。絞り込まずに全部選んでオンにしてもらうのが確実
