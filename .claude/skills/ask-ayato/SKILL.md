# あやとに判断を仰ぐ

## 0. まず、聞くことかどうか

**やり方・順番・品質は、こちらの責務。聞かない。**
聞くのは**仕様そのもの**（あやとが何を求めているか）だけ。

> 仕様の認識が合わない場合は聞けと言ってるだろう。
> ユーザーが求めてる仕様がわからないならヒアリングしろよ。（あやと 2026-09-19）

迷ったら: **自分の読み方で埋めると、出したあとに全部やり直しになるか？**
なるなら聞く。ならないなら決めて、やって、報告する。

## 1. チャットで聞かない。issue を立てる

会話に埋もれるし、セッションが変わると消える。
**あとから「何を聞いて、何と答えたか」を引けるように残す。**

## 2. 聞く前に、いま動いているものを数える

**「どうしますか」だけを投げない。** いまの実装が何をしていて、**実測でどうなっているか**を先に出す。
選択肢と、選んだ場合の数字を並べる。**決める人が計算しなくていいように。**

## 3. 通知を飛ばす ← **いちばん外しやすいところ**

> 私のアカウントでメンションしても通知来ないのでGitHub action 経由とかで。（あやと 2026-10-08）

**セッションから issue に書くときは、あやと本人のトークンで書いている。**
GitHub は**自分で自分を呼んでも通知を飛ばさない。**

つまり `@Ayato-kosaka` と書いても **1通も届かない。**
**字としては在るので、書いたほうは届いた気になる。** これがいちばん悪い。

### 飛ばすには、ワークフローを押す

```bash
gh api -X POST repos/Ayato-kosaka/live-streaming/actions/workflows/call_ayato.yml/dispatches \
  -f ref=master -f 'inputs[issue]=701' -f 'inputs[text]=画像をどこに置くか決めてください'
```

`github-actions[bot]` が書くので、はじめて通知になる。

### 2つ、気をつける

- **`@Ayato-kosaka` を囲い・引用・バッククォートの中に入れない。**
  コードブロック（``` や4つ空白）・行頭の `>`・`` `@Ayato-kosaka` `` は、
  **字として在っても飛ばない。** 判定は `python/ticket_labels.py` の `mention_live()`。
  人の目で見ないで、これに通して確かめる
- **入れた字は公開のログに出る。** このリポジトリは公開で、Actions のログも誰でも読める。
  **視聴者さんの素性（名前・channelId・どねID・uid・ハンドル）を `text` に入れない。**
  入れたいことは issue の本文に書いて、`text` からは「#NNN を見て」とだけ言う

## 4. 待ち札に、理由を1行

`待ち-あやと` を付けたら、その issue に**何を待っているか**を1行書く。
書かないと、札だけ在って何待ちか分からない札になる。

## 5. 答えを待つあいだは止まらない

**1件の回答待ちで全部を止めない。** 他の作業を進める。
止めると、こちらの手が空くだけで誰も得をしない。

## 6. 答えが来たら、その場で反映して閉じる

**あとでまとめて、にしない。** セッションが変わると「やったかどうか」が分からなくなる。
決まったことは issue に書き戻す（**次に読む人が、決定だけを読めるように**）。
